ROCm is an Advanced Micro Devices (AMD) software stack for graphics processing unit (GPU) programming. ROCm spans several domains, including general-purpose computing on graphics processing units (GPGPU), high-performance computing (HPC), and heterogeneous computing. It offers several programming models: HIP (GPU-kernel-based programming), OpenMP (directive-based programming), and OpenCL.
ROCm is free, libre and open-source software (except the GPU firmware blobs[3]), and it is distributed under various licenses. The name initially stood for Radeon Open Compute platform;[4] however, due to Open Compute being a registered trademark, the name no longer functions as an acronym.[5][non-primary source needed]
Background
[edit]
The first GPGPU software stack from ATI/AMD was Close to Metal, which became Stream.
ROCm was launched around 2016[6] with the Boltzmann Initiative.[7] ROCm stack builds upon previous AMD GPU stacks; some tools trace back to GPUOpen and others to the Heterogeneous System Architecture (HSA).
In July 2026, AMD announce ROCm will be on six week release cycle.[8]
Heterogeneous System Architecture Intermediate Language
[edit]
HSAIL[9] was aimed at producing a middle-level, hardware-agnostic intermediate representation that could be JIT-compiled to the eventual hardware (GPU, FPGA...) using the appropriate finalizer. This approach was dropped for ROCm: now it builds only GPU code, using LLVM, and its AMDGPU backend that was upstreamed,[10] although there is still research on such enhanced modularity with LLVM MLIR.[11]
Programming abilities
[edit]
ROCm as a stack ranges from the kernel driver to the end-user applications. AMD has introductory videos about AMD GCN hardware,[12] and ROCm programming[13] via its learning portal.[14]
One of the best technical introductions about the stack and ROCm/HIP programming, remains, to date, to be found on Reddit.[15]
Hardware support
[edit]
ROCm is primarily targeted at discrete professional GPUs,[16] but consumer GPUs and APUs of the same architecture as a supported professional GPU are known to work with ROCm. For example, all professional GPUs of the RDNA 2 architecture are officially supported by ROCm 5.x; users report that Consumer RDNA2 units such as the Radeon 6800M APU and the Radeon 6700XT GPU also work.[17]

Other languages
[edit]
Julia
[edit]
Julia has the AMDGPU.jl package,[34] which integrates with LLVM and selects components of the ROCm stack. Instead of compiling code through HIP, AMDGPU.jl uses Julia's compiler to generate LLVM IR directly, which is later consumed by LLVM to generate native device code. AMDGPU.jl uses ROCr's HSA implementation to upload native code onto the device and execute it, similar to how HIP loads its own generated device code.
AMDGPU.jl also supports integration with ROCm's rocBLAS (for BLAS), rocRAND (for random number generation), and rocFFT (for FFTs). Future integration with rocALUTION, rocSOLVER, MIOpen, and certain other ROCm libraries is planned.
Software distribution
[edit]
Official
[edit]
Installation instructions are provided for Linux and Windows in the official AMD ROCm documentation.[35] ROCm software is currently spread across several public GitHub repositories. Within the main public meta-repository,[36] there is an XML manifest[37] for each official release: using git-repo,[38] a version control tool built on top of Git, is the recommended way to synchronize with the stack locally.[39]
AMD starts distributing containerized applications for ROCm, notably scientific research applications gathered under AMD Infinity Hub.[40][41]
AMD itself distributes packages tailored to various Linux distributions.[42]
Third-party
[edit]
There is a growing third-party ecosystem packaging ROCm.[43][better source needed]
Linux distributions are officially packaging (natively) ROCm, with various degrees of advancement: Arch Linux,[44] Gentoo,[45] Debian, Fedora ,[46] GNU Guix, and NixOS.
Components
[edit]
There is one kernel-space component, ROCk, and the rest – there is roughly a hundred components in the stack – is made of user-space modules.
The unofficial typographic policy is to use: uppercase ROC, lowercase following for low-level libraries, i.e. ROCt, and the contrary for user-facing libraries, i.e. rocBLAS.[48]
AMD is active developing with the LLVM community, but upstreaming is not instantaneous, and as of January 2022, is still lagging.[49] AMD still officially packages various LLVM forks[50][51][11] for parts that are not yet upstreamed – compiler optimizations destined to remain proprietary, debug support, OpenMP offloading, etc.
Low-level
[edit]
ROCk – Kernel driver
[edit]
ROCm – Device libraries
[edit]
Support libraries implemented as LLVM bitcode. These provide various utilities and functions for math operations, atomics, queries for launch parameters, on-device kernel launch, etc.[52]
ROCt – Thunk
[edit]
The thunk is responsible for all the thinking and queuing that goes into the stack.[53]
ROCr – Runtime
[edit]
The ROC runtime is a set of APIs/libraries that allows the launch of compute kernels by host applications.[54] It is AMD's implementation of the HSA runtime API.[55] It is different from the ROC Common Language Runtime.
ROCm – CompilerSupport
[edit]
ROCm code object manager is in charge of interacting with LLVM intermediate representation.[56]
Mid-level
[edit]
ROCclr Common Language Runtime
[edit]
The common language runtime is an indirection layer adapting calls to ROCr on Linux and PAL on windows.[57] It used to be able to route between different compilers, like the HSAIL-compiler. It is now being absorbed by the upper indirection layers (HIP and OpenCL).
OpenCL
[edit]
ROCm ships its installable client driver (ICD) loader and an OpenCL[58] implementation bundled together.[59] As of January 2022, ROCm 4.5.2 ships OpenCL 2.2, and is lagging behind competition.[60]
HIP – Heterogeneous Interface for Portability
[edit]
The AMD implementation for its GPUs is called HIPAMD.[61][62] There is also a CPU implementation] mostly for demonstration purposes.[63]
HIPCC
[edit]
HIP builds a HIPCC compiler that either wraps Clang and compiles with LLVM open AMDGPU backend, or redirects to the NVIDIA compiler.[64]
HIPIFY
[edit]
HIPIFY is a source-to-source compiling tool.[65] It translates CUDA to HIP and reverse, either using a Clang-based tool, or a sed-like Perl script.
GPUFORT
[edit]
Like HIPIFY, GPUFORT is a tool compiling source code into other third-generation-language sources, allowing users to migrate from CUDA Fortran to HIP Fortran.[66] It is also in the repertoire of research projects, even more so.[67]
High-level
[edit]
ROCm high-level libraries are usually consumed directly by application software, such as machine learning frameworks. Most of the following libraries are in the General Matrix Multiply (GEMM) category, which GPU architecture excels at.
The majority of these user-facing libraries comes in dual-form: hip for the indirection layer that can route to Nvidia hardware, and roc for the AMD implementation.[68]
rocBLAS / hipBLAS
[edit]
rocBLAS[69] and hipBLAS[70] are central in high-level libraries, it is the AMD implementation for Basic Linear Algebra Subprograms. It uses the library Tensile privately.[71]
rocSOLVER / hipSOLVER
[edit]
This pair of libraries constitutes the LAPACK implementation for ROCm and is strongly coupled to rocBLAS.
Utilities
[edit]
Comparison with competitors
[edit]
ROCm competes with other GPU computing stacks: Nvidia CUDA and Intel OneAPI.
Nvidia CUDA
[edit]
Nvidia's CUDA is closed-source, whereas AMD ROCm is open source. There is open-source software built on top of the closed-source CUDA, for instance RAPIDS.[73]
CUDA is able to run on consumer GPUs, whereas ROCm support is mostly offered for professional hardware such as AMD Instinct and AMD Radeon Pro.
Nvidia provides a C/C++-centered frontend and its Parallel Thread Execution (PTX) LLVM GPU backend as the Nvidia CUDA Compiler (NVCC).
Intel OneAPI
[edit]
All the oneAPI corresponding libraries are published on its GitHub Page.[74]
Unified Acceleration Foundation (UXL)
[edit]
Unified Acceleration Foundation (UXL) is a new technology consortium that are working on the continuation of the OneAPI initiative, with the goal to create a new open standard accelerator software ecosystem, related open standards and specification projects through Working Groups and Special Interest Groups (SIGs). The goal will compete with Nvidia's CUDA. The main companies behind it are Intel, Google, Arm, Qualcomm, Samsung, Imagination, and VMware.[75]

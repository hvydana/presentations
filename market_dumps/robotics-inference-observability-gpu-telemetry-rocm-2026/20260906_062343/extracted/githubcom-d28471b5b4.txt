Observability and performance-optimisation platform for NVIDIA AI inference workloads. It collects GPU, host and inference telemetry, persists and aggregates it, detects anomalies, and produces root-cause diagnoses backed by the measurements it actually observed.
GPU / host telemetry ──┐
inference requests ────┼──► aggregation ──► diagnostics ──► "GPU utilisation is
batching signals ──────┘                    (15 rules)      32.8% because batches
                                                            average 2.3 of 32"
No fabricated data. Every displayed number traces to a stored sample. A
metric that was not measured returns null and renders as —, never 0. With
no NVIDIA GPU present the platform states that plainly instead of inventing
hardware statistics.
Demo data is quarantined. Every telemetry row carries a data_source of
production or demo; every read filters on it. Synthetic data can never be
presented as production telemetry.
Diagnosis without an LLM. Fifteen deterministic rules run against stored measurements and produce the full structured diagnosis — title, severity, root cause, evidence, metrics, impact, recommendations and confidence. A language model is optional and only ever narrates findings it did not compute.
The agent cannot do damage. All 11 agent tools are read-only. There is no tool to run a command, write data, or read secrets — enforced by absence of the capability, not by prompt instructions.

Demo Mode generates coherent synthetic telemetry for seven scenarios. Each produces physically consistent signals, so the diagnostics engine has something real to reason about.
| Scenario | Signals | Expected diagnosis | 
|---|---|---|
| Healthy GPU | High utilisation, batches near max, stable latency | healthy | 
| Under-batching | Batch 2.3/32, GPU ~33%, low queue time | under_batching | 
| VRAM pressure | VRAM >96%, elevated errors, heavy tail | vram_saturation | 
| CPU bottleneck | CPU ~96%, GPU ~37%, high queue time | cpu_bottleneck | 
| Latency spike | P95 rising sharply, P99/P50 ≈ 8× | latency_spike | 
| Throughput degradation | Throughput declining, demand steady | throughput_degradation | 
| Thermal throttling | >85 °C, SM clock at 62% of rated | thermal_throttling | 
Switch scenarios from Workloads, or:
curl -X POST "http://localhost:8000/api/v1/demo/scenario" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"scenario":"under_batching"}'
Demo data lives in its own namespace and is deleted independently:
curl -X DELETE "http://localhost:8000/api/v1/demo/data" -H "Authorization: Bearer $TOKEN"
Requires the NVIDIA driver, Container Toolkit, and DEMO_MODE=false.
# 1. Install the NVIDIA Container Toolkit, then verify:
docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi
# 2. Mint an agent credential:
python scripts/create_api_key.py --name telemetry-agent \
  --scopes telemetry:read telemetry:write
# 3. Start with the GPU profile:
DEMO_MODE=false AGENT_API_KEY=nvo_live_... docker compose --profile gpu up -d
On Kubernetes the agent runs as a DaemonSet restricted to nodes labelled
nvidia.com/gpu.present=true. See docs/DEPLOYMENT.md.
If no GPU is detected the platform reports nvml_available: false with a
specific reason and shows an explicit "NVIDIA GPU unavailable" notice.
See docs/ARCHITECTURE.md for seven Mermaid diagrams covering system architecture, telemetry flow, inference flow, diagnosis flow, the ER model, and both deployment topologies.

- Per-process GPU accounting requires NVML process APIs, which are unavailable in some virtualised and MIG configurations. The UI states this rather than showing an empty table without explanation.
- Cost is an estimate, computed as observed GPU-hours × a configurable rate. It is not billing data and is labelled as an estimate everywhere.
- The bundled PostgreSQL and Redis manifests are for evaluation. Use a managed service or an operator in production.
- The local inference adapter performs no model computation. It exists so the gateway and its instrumentation can be exercised without a serving backend, and it says so in its own response payload.
- Model comparison needs traffic on both models. With data on only one, the tool declines to recommend rather than guessing.

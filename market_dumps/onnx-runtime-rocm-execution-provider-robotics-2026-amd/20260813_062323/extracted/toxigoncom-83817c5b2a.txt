What Actually Slows Down Your ONNX Models
Most optimization guides focus on the obvious - batch size, precision, and operator fusion. But the real performance killers are often hiding in plain sight. Here's what's actually making your model crawl.
Memory Access Patterns
ONNX models don't run in isolation - they're at the mercy of how your hardware moves data around. The biggest culprit? Poor memory locality.
When your model's weights and activations are scattered across memory, the CPU or GPU spends more time waiting for data than actually computing.
Consider a simple convolution layer. If the input tensor isn't contiguous in memory, the GPU might need to make multiple memory accesses to gather all the data it needs. This is especially bad on newer GPUs with large L2 caches - they're designed to handle contiguous memory accesses efficiently, but non-contiguous data forces them to fall back to slower global memory.
You can check for this with NVIDIA's Nsight Compute or AMD's ROCProfiler. Look for high "memory replay" or "memory dependency" metrics. If you see these, your model is spending more time waiting for data than computing.
Operator Inefficiency
Not all ONNX operators are created equal. Some are hardware-optimized, while others run on the CPU fallback. The Gather operator is a common offender - it's often used for embedding lookups, but many implementations don't leverage GPU memory coalescing.
Here's a real-world example: replacing Gather with GatherElements in a recommendation model reduced inference time by 22% on NVIDIA A100 GPUs. The newer operator better utilizes the GPU's memory hierarchy.
Another trap is using Reshape when you could use Flatten or Squeeze. Reshape operations often trigger memory copies, while the more specific operators can sometimes be optimized away entirely.
Graph Structure Bloat
Every node in your ONNX graph adds overhead. The runtime needs to schedule the operation, allocate memory for inputs and outputs, and manage dependencies. A model with 10,000 nodes will almost always be slower than an equivalent model with 1,000 nodes, even if they perform the same computation.
Common sources of bloat:
- Unnecessary identity operations (from framework exports)
- Redundant type conversions
- Dead code that never executes
- Overly granular operations that could be fused
In 2025, Meta published a case study showing how they reduced their recommendation model's graph size by 40% through operator fusion and dead code elimination. The result? 18% faster inference with no accuracy loss.
Hardware Mismatch
ONNX Runtime supports multiple execution providers, but using the wrong one can tank performance. For example, running a model on CUDA when you're actually using an AMD GPU means falling back to CPU execution. Even worse, some providers have hidden overhead - the TensorRT provider might add 5-10ms of initialization time, which matters if you're doing single-batch inference.

Precision Pitfalls
Quantization is a double-edged sword. While reducing precision from FP32 to INT8 can give you 2-4x speedup, it's not always a free lunch. The performance gain depends heavily on your hardware:
- NVIDIA GPUs: INT8 is 2-4x faster than FP32 on Ampere and newer architectures
- AMD GPUs: INT8 is about 2x faster on CDNA 2/3
- Intel CPUs: INT8 is 2-3x faster on Xeon Scalable processors
- Apple Silicon: INT8 is only 1.5x faster than FP16 on M-series chips
But here's the catch: not all operations benefit equally from quantization. Matrix multiplications see the biggest gains, while element-wise operations often see little to no improvement. In some cases, quantizing everything can actually make your model slower because the runtime needs to constantly convert between precisions.
Batch Size Gotchas
Most guides tell you to increase batch size for better throughput. That's true up to a point, but there are diminishing returns. The optimal batch size depends on:
- Your GPU's memory capacity
- The size of your model
- Your latency requirements
- Whether you're using dynamic batching
For example, on an NVIDIA A100 with 40GB of memory, a ResNet-50 model hits peak throughput at batch size 64. Beyond that, the performance gains are minimal (less than 5% improvement from 64 to 128), but memory usage keeps increasing linearly.
Dynamic batching (where you process multiple requests of different sizes together) adds another layer of complexity. ONNX Runtime's dynamic batching support improved in 2025, but it still has overhead. The runtime needs to pad inputs to the same size, which wastes computation on the padded values.

Extreme quantization
FP8 is the new kid on the block. Introduced in NVIDIA's H100 and AMD's MI300, it offers a good balance between size and accuracy. The format uses 1 sign bit, 5 exponent bits, and 2 mantissa bits, giving it a range of ±448. This is enough for most inference tasks while cutting memory usage in half compared to FP16.
When to Use Each Precision
Here's a practical guide to choosing precision:
- FP32: Use when accuracy is critical and you have no performance constraints. Also use for the first and last layers of quantized models (these are often sensitive to precision).
- FP16/BF16: Good for mixed precision training and inference on GPUs that support it. BF16 is better for training because it has the same range as FP32.
- FP8: Best for inference on supported hardware (H100, B100, MI300).
Offers similar accuracy to FP16 with better performance.
- INT8: The sweet spot for most inference tasks. Works on all hardware and gives 2-4x speedup over FP32.
- INT4: Use only when you need extreme compression (e.g., edge devices). Expect some accuracy loss.
Quantization Techniques
There are several ways to quantize a model:
1. Post-Training Quantization (PTQ)
This is the simplest approach - you take a trained FP32 model and convert it to lower precision. The process:
- Export your model to ONNX
- Run calibration on a representative dataset
- Apply quantization
- Validate accuracy
PTQ works well for most models, but it can cause accuracy loss for sensitive architectures. The key is using a good calibration dataset - it should be representative of your production data.
Here's how to do PTQ with ONNX Runtime:
import onnxruntime as ort
from onnxruntime.quantization import quantize_dynamic, QuantType
# Load model
model_path = 'model.onnx'
quantized_model_path = 'model_quantized.onnx'
# Quantize to INT8
quantize_dynamic(
    model_path,
    quantized_model_path,
    weight_type=QuantType.QUInt8
)
# Verify
session = ort.InferenceSession(quantized_model_path)
2. Quantization-Aware Training (QAT)
QAT simulates quantization during training, which helps the model adapt to lower precision. This typically gives better accuracy than PTQ but requires retraining.
PyTorch's QAT support improved significantly in 2025. Here's a basic example:

train_model(model)
# Convert to quantized model

- FP32 for the first and last layers
- FP16 for attention layers

Handling Quantization Challenges
Quantization isn't always smooth sailing. Here are common issues and how to fix them:
1. Accuracy Loss
If your quantized model loses too much accuracy:
- Try QAT instead of PTQ
- Use a larger calibration dataset
- Keep sensitive layers in FP32
- Adjust the quantization range (some tools let you specify min/max values)
2. Unsupported Operations
Some operations don't quantize well. Common offenders:
- Softmax with large input ranges
- LayerNorm with small epsilon values
- Custom operations
Solutions:
- Replace problematic operations with quantized equivalents
- Implement custom quantization for unsupported ops
- Keep problematic ops in FP32
3. Dynamic Range Issues
Some models have activations with very large or very small ranges. This can cause problems with fixed-point quantization.
Solutions:
- Use per-channel quantization instead of per-tensor
- Apply range clipping before quantization
- Use FP8 instead of INT8 (if hardware supports it)
Advanced Techniques
For when basic quantization isn't enough:
1. Sparse Quantization
Many models have weights that can be pruned without accuracy loss. Sparse quantization combines pruning with quantization to get even better compression.
TensorRT 10.0 added support for structured sparsity patterns. Here's how to enable it:

2. Quantization with Knowledge Distillation
Train a smaller, quantized model to mimic a larger FP32 model. This can give you better accuracy than direct quantization.
Example workflow:
- Train a large FP32 teacher model
- Create a smaller student model architecture
- Train the student with both the original loss and a distillation loss
- Quantize the student model
3. Learned Quantization
Instead of using fixed quantization parameters, learn them during training. This can give better accuracy than static quantization.
PyTorch's learnable_quantize module (added in 2025) makes this easier:

Graph Surgery That Doesn't Require a PhD
You don't need to be a compiler expert to optimize your ONNX graph. Here are simple but effective techniques that give you most of the benefit with minimal effort.
Operator Fusion
Operator fusion combines multiple operations into a single kernel, reducing memory access and kernel launch overhead. Common fusion patterns:
- Conv + BatchNorm + ReLU → ConvBnRelu
- MatMul + Add → Gemm
- Concat + Slice → optimized memory access
- Reduce + Reshape → single operation
ONNX Runtime automatically fuses many common patterns, but you can help it by structuring your model appropriately. For example, if you're using PyTorch, export with torch.onnx.export(..., do_constant_folding=True) to enable constant folding during export.
Here's how to check what fusions ONNX Runtime applied:
import onnxruntime as ort
options = ort.SessionOptions()
options.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
options.log_severity_level = 0  # Enable logging
session = ort.InferenceSession('model.onnx', options)
The logs will show which operators were fused.
Dead Code Elimination
Many models contain operations that never execute or don't affect the output. Common examples:
- Unused branches in control flow
- Operations that only affect intermediate values
- Duplicate operations
- Identity operations (e.g., Add(0, x))
The onnx-simplifier tool automatically removes dead code. Here's how to use it:
python -m onnxsim model.onnx model_simplified.onnx
In one case study, this reduced a model's node count from 1,243 to 876 (30% reduction) with no accuracy loss.
Constant Folding
Constant folding evaluates constant expressions at optimization time rather than runtime. For example:
# Before
x = 2 * 3  # Computed at runtime
# After
x = 6      # Computed at optimization time
This is especially useful for:
- Model hyperparameters
- Normalization constants
- Static embeddings
- Shape calculations
ONNX Runtime performs constant folding automatically when you set graph_optimization_level=ORT_ENABLE_ALL. You can also do it manually with onnxruntime-tools:
python -m onnxruntime.tools.net_drawer --input model.onnx --output model_folded.onnx --fold_const
Memory Optimization
ONNX models can waste memory by keeping intermediate tensors alive longer than necessary. Here are ways to optimize memory usage:
1. In-Place Operations
Some operations can modify their input tensor in-place rather than allocating a new output tensor.
Common in-place operations:
- Add (when output is same as one input)
- Mul
- Sub
- Div
To enable in-place operations in ONNX Runtime:
options = ort.SessionOptions()
options.add_session_config_entry('session.inplace_ops', '1')
2. Memory Reuse
ONNX Runtime can reuse memory buffers for tensors with compatible shapes. This is especially useful for models with dynamic shapes.
To enable memory reuse:
options = ort.SessionOptions()
options.add_session_config_entry('session.memory_reuse', '1')
3. Output Reuse
If your model has multiple outputs that aren't all needed, you can tell ONNX Runtime to only compute the ones you want:
session = ort.InferenceSession('model.onnx')
outputs = session.run(['output1'], {'input': input_data})  # Only compute output1

When Optimization Goes Wrong (And How to Fix It)
Optimization isn't always a straight path to better performance. Sometimes, your "optimized" model runs slower than the original. Here's why it happens and how to fix it.
Over-Optimizing for Specific Hardware
Hardware-specific optimizations can backfire when the model runs on different hardware. Common issues:
- TensorRT optimizations that don't work on AMD GPUs
- AVX-512 instructions that crash on older Intel CPUs
- FP16 models that run slowly on hardware without FP16 support
How to fix it:
- Maintain multiple model versions for different hardware
- Use ONNX Runtime's dynamic execution provider selection
- Implement fallback strategies
- Test on all target hardware
Example fallback strategy:
def get_execution_providers():
    providers = []
    # Check for NVIDIA GPU
    try:
        import pynvml
        pynvml.nvmlInit()
        device_count = pynvml.nvmlDeviceGetCount()
        if device_count > 0:
            providers.append('TensorrtExecutionProvider')
            providers.append('CUDAExecutionProvider')
    except:
        pass
    # Check for AMD GPU
    try:
        import pyamdgpuinfo
        if pyamdgpuinfo.detect_gpus():
            providers.append('ROCMExecutionProvider')
    except:
        pass
    # Check for Intel CPU
    try:
        import cpuinfo
        if 'intel' in cpuinfo.get_cpu_info()['brand_raw'].lower():
            providers.append('DnnlExecutionProvider')
    except:
        pass
    # Fall back to CPU
    providers.append('CPUExecutionProvider')
    return providers
Ignoring Memory Bandwidth
Many optimizations focus on compute performance but ignore memory bandwidth. This can lead to:
- Models that are compute-bound on paper but memory-bound in practice
- Quantized models that run slower because of memory access patterns
- Large batch sizes that saturate memory bandwidth
How to fix it:
- Profile memory bandwidth usage (use NVIDIA Nsight, AMD ROCProfiler, or Intel VTune)
- Optimize memory access patterns (make tensors contiguous, use memory reuse)
- Reduce model size (quantization, pruning)
- Adjust batch size to match memory bandwidth
Example memory bandwidth analysis with NVIDIA Nsight:
ncu --set full --metrics dram__bytes.sum, sm__throughput.avg.pct_of_peak_sustained_elapsed ./your_inference_script
If dram__bytes.sum is high and sm__throughput.avg.pct_of_peak_sustained_elapsed is low, your model is memory-bound.
Overhead from Dynamic Shapes
Dynamic shapes add flexibility but can introduce significant overhead:
- Runtime shape inference
- Memory reallocation for different input sizes
- Kernel recompilation for different shapes
How to fix it:
- Use static shapes when possible
- For dynamic shapes, specify a limited set of possible shapes
- Use ONNX Runtime's shape inference optimization
- Consider maintaining separate models for different shape ranges
Example of specifying dynamic shapes in ONNX:
# When exporting from PyTorch
torch.onnx.export(
    model,
    dummy_input,
    "model.onnx",
    dynamic_axes={
        'input': {0: 'batch_size', 2: 'height', 3: 'width'},  # Only these axes are dynamic
        'output': {0: 'batch_size'}
    }
)
Quantization Gone Wrong
Quantization can cause accuracy loss or even performance degradation if not done carefully:
- Models with large dynamic ranges that don't fit in INT8
- Operations that don't benefit from quantization (e.g., element-wise ops)
- Quantization that forces precision conversions at runtime
How to fix it:
- Use per-channel quantization instead of per-tensor
- Keep sensitive layers in FP32
- Use mixed precision quantization
- Validate accuracy after quantization
- Profile to ensure quantization actually improves performance
Example of mixed precision quantization:
from onnxruntime.quantization import quantize_dynamic, QuantType
# Quantize most layers to INT8 but keep first and last layers in FP32
quantize_dynamic(
    "model.onnx",
    "model_quant.onnx",
    weight_type=QuantType.QUInt8,
    nodes_to_exclude=['/model/first_layer', '/model/last_layer']  # Keep these in FP32
)
Operator Fusion Pitfalls
Operator fusion can sometimes make things worse:
- Fused kernels that are less efficient than individual operations
- Fusion that prevents other optimizations
- Fusion that increases memory usage
How to fix it:
- Profile with and without fusion
- Use ONNX Runtime's fusion control options
- Manually specify which operations to fuse
Example of controlling fusion in ONNX Runtime:
options = ort.SessionOptions()
options.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_EXTENDED
options.add_session_config_entry('session.disable_fusion', 'Add, Sub, Mul')  # Disable fusion for these ops
Threading Issues
Too many threads can hurt performance due to:
- Thread creation overhead
- Cache contention
- False sharing
- Load imbalance
How to fix it:
- Set thread count to match your CPU cores
- Use thread pooling instead of creating new threads for each request
- Profile with different thread counts
- Consider using ONNX Runtime's intra/inter-op parallelism settings
Example of setting thread counts:
options = ort.SessionOptions()
options.intra_op_num_threads = 4  # Number of threads for single operation
options.inter_op_num_threads = 2  # Number of threads for parallel operations
Memory Management Mistakes
Poor memory management can lead to:
- Memory leaks
- High memory usage
- Frequent memory allocation/deallocation
- Memory fragmentation
How to fix it:
- Enable memory reuse in ONNX Runtime
- Use memory pools
- Limit batch size to control memory usage
- Profile memory usage with tools like Valgrind or Heaptrack
Example memory configuration:
options = ort.SessionOptions()
options.add_session_config_entry('session.memory_reuse', '1')
options.add_session_config_entry('session.arena_extend_strategy', 'kSameAsRequested')
Debugging Slow Optimized Models
When your optimized model runs slower than the original, follow this debugging process:
- Verify the optimization was applied: Check the model with Netron to see if the optimizations are actually present.
- Profile the original and optimized models: Use NVIDIA Nsight, AMD ROCProfiler, or Intel VTune to compare performance characteristics.
- Check for precision conversions: Quantized models might be converting between precisions at runtime.
- Examine memory usage: The optimized model might be using more memory, causing swapping or cache misses.
- Test with different batch sizes: Some optimizations only help at specific batch sizes.
- Try different execution providers: The optimization might be specific to a particular provider.
- Check for kernel launch overhead: Small models might suffer from too many small kernel launches.
Example profiling with NVIDIA Nsight:
# Profile original model
ncu --set full --metrics sm__cycles_elapsed.avg, sm__inst_executed.sum ./original_model
# Profile optimized model
ncu --set full --metrics sm__cycles_elapsed.avg, sm__inst_executed.sum ./optimized_model
Common Optimization Anti-Patterns
Avoid these common mistakes:
- Optimizing without profiling: Always profile before and after optimization to verify improvements.
- Over-quantizing: Not all operations benefit from quantization. Keep sensitive layers in higher precision.
- Ignoring memory bandwidth: A compute-optimized model might still be memory-bound.
- Using dynamic shapes unnecessarily: Static shapes are always faster when possible.
- Not testing on target hardware: Optimizations that work on your development machine might not work in production.
- Chasing marginal gains: Focus on optimizations that give significant improvements, not 1-2% speedups.
- Ignoring framework overhead: Sometimes the bottleneck is in the framework, not the model.
